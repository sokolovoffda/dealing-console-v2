# AGENTS.md — правила работы Codex в проекте


# Входные данные
На вход ты получаешь:
- **Кейс (основная задача):** 
Реализовать в Electron-версии пульта встроенную диагностику для сбора, просмотра и выгрузки технических логов.

Что хотим сейчас: разработать базу пока без пароля, отправки на сервер. Необходимо реализовать кнопку-заглушку которая снимает или выводит в самое простое модальное окно логи по категориям за некоторый период.

Что хотим по итогу

Добавить защищённый вход в диагностический режим по паролю. (энпоинт проверки пароля администратора)
Дать пользователю возможность открыть модалку/экран диагностики и просматривать логи по категориям.
Дать возможность выгружать диагностический архив или отдельно файлы логов по категориям. (эндпоинт для отправки файлов нам на сервер)
Ограничить повторный запуск выгрузки через cooldown на кнопку. (нужно обсудить ограничения на отправку логов нам на сервер со стороны пользователя)
Пользовательский сценарий

Пользователь открывает раздел диагностики.
Вводит пароль администратора.
После успешной авторизации видит список категорий логов.
Может просмотреть логи конкретной категории в интерфейсе/модалке.
Может нажать кнопку отправки. (обсудить: отправка отдельных категорий логов возможна или отправляется все логи за некоторый период, по всем категориям)
Кнопка выгрузки временно блокируется на таймаут.
Какие логи собираем

Console logs
Логи renderer-процесса: log, info, warn, error, debug.
Main process logs
Логи Electron main process, IPC-ошибки, системные события окна/загрузки.
Network HAR
HTTP/HTTPS-запросы приложения в формате HAR.
WebSocket trace
События и сообщения по /sip ( /im - будет перенесен на rest api), локальному controller websocket ws://127.0.0.1:8765.
WebRTC stats
Snapshot статистики активных/последних RTC-сессий на момент выгрузки.
App metadata
Версия приложения, платформа, время, текущий маршрут, пользователь, hostname, состояние сети.
Категории для просмотра в интерфейсе

Console
Network
WebSocket
WebRTC
System / Electron
Технические требования

Функционал работает только в Electron.
Сбор данных идёт через Electron main process + IPC bridge.
Логи хранятся в ring buffer, чтобы были доступны до нажатия кнопки.
Перед показом и выгрузкой данные проходят маскировку чувствительных значений.
Формат и состав архива должны быть стабильны для дальнейшей отправки на сервер.


**Кейс → План → Одобрение пользователя → Реализация по шагам → Пользователь коммитит → Следующий шаг → Обновление проектной памяти при необходимости.**

Этот файл является **постоянной инструкцией проекта**. Он не должен содержать текст конкретной задачи, Jira-кейса, временных уточнений или плана реализации.

Все рабочие материалы агента хранятся в единой служебной директории `.ai/`.

Конкретные задачи и проектная память хранятся отдельно:

- `.ai/tasks/WUI-XXXX/case.md` — описание конкретного кейса.
- `.ai/tasks/WUI-XXXX/implementation_plan_N.md` — план реализации конкретной части кейса.
- `.ai/knowledge/wiki/` — долгоживущая проектная память: доменная логика, архитектура, решения, ограничения.
- `.ai/knowledge/raw/` — исходные материалы: документы, заметки, скриншоты, выгрузки, описания текущей реализации.

Главный приоритет — минимальные изменения, понятный review, сохранение текущей логики и накопление проектных знаний без выдумывания.

# 1. Главные правила

1. Всегда прочитай правила проекта в `.cursor`, если эта директория есть.
2. Не заменяй целые файлы, если можно внести точечный патч.
3. Не делай скрытый рефакторинг и не исправляй соседние проблемы «заодно».
4. Не меняй публичные контракты без необходимости:
   - props;
   - emits;
   - store API;
   - route names;
   - DTO;
   - IPC contracts;
   - socket/event contracts;
   - экспортируемые типы.
5. Не добавляй новые зависимости без отдельного согласования с пользователем.
6. Не удаляй комментарии, если логика блока кода осталась прежней.
7. Если логика изменилась, аккуратно обнови комментарий. Русские комментарии должны остаться читаемыми.
8. Не удаляй закомментированный код, если это не является явной частью задачи.
9. Проверяй, что кодировка файлов не нарушена. Особенно внимательно проверяй кириллицу.
10. Работай только в рамках текущей ветки и текущего шага.
11. Если задача требует плана, не пиши код до явного одобрения плана пользователем.
12. Никогда не записывай описание текущей задачи в `AGENTS.md`.
13. Создание новых файлов всегда должно соответствовать fsd. уточнять у пользователя. все импорты через index.ts. запрещаются относительные импорты.
14. Не создавай чрезмерное количество helper-функций и абстракций. Код должен оставаться человекочитаемым: пиши логику прямо в месте использования, если так проще читать, а helper выноси только когда он убирает реальное дублирование, упрощает сложный блок или соответствует существующему паттерну проекта.
15. Пиши код для человеческого review, а не «машинный» код. Избегай бесполезной вложенности, цепочек одноразовых wrapper-функций, alias-функций без смысла и дробления простого сценария на слишком много мелких helper-ов. Review должен позволять быстро проследить основной сценарий сверху вниз; если helper нужен, его назначение должно быть очевидно из имени и он должен реально упрощать чтение.

# 2. Где хранить задачу, план и знания

## 2.1. `AGENTS.md`

`AGENTS.md` содержит только постоянные правила работы агента в проекте.

В `AGENTS.md` нельзя хранить:

- текст текущей задачи;
- Jira-описание;
- временные уточнения пользователя;
- план реализации;
- список выполненных шагов;
- заметки по конкретному багу.

## 2.2. `.ai/tasks/WUI-XXXX/case.md`

`case.md` — это самодостаточное описание конкретной задачи.

Создавай или обновляй его, когда пользователь просит план по Jira-кейсу или большой задаче.

Формат:

```markdown
# WUI-XXXX — [Краткое название]

## Исходная задача

[Описание задачи из Jira, сообщения пользователя или другого источника]

## Уточнения пользователя

- [Уточнение 1]
- [Уточнение 2]

## Ограничения

- [Техническое или продуктовое ограничение]

## Связанные материалы

- [Ссылки на файлы, скриншоты, wiki-страницы, если есть]
```

Правила:

1. `case.md` должен быть понятен без чтения чата.
2. Если пользователь даёт новое важное уточнение по текущему кейсу, добавь его в `case.md`.
3. Не перезаписывай старые уточнения без необходимости.
4. Если уточнение отменяет старое решение, добавь это явно.

## 2.3. `.ai/tasks/WUI-XXXX/implementation_plan_N.md`

`implementation_plan_N.md` — это план реализации конкретной части кейса.

Правила:

1. План всегда создаётся отдельным файлом.
2. Если план уже есть, не перезаписывай его без явной просьбы пользователя.
3. Для следующей части создай следующий номер:
   - `implementation_plan_1.md`
   - `implementation_plan_2.md`
   - `implementation_plan_3.md`
4. В начале плана добавляй краткое описание текущей части кейса из `case.md` или из сообщения пользователя.
5. Не ссылайся на `AGENTS.md` как на источник описания задачи.
6. Каждый шаг плана должен быть атомарным и проверяемым.
7. Один шаг плана соответствует одному будущему коммиту пользователя.

## 2.4. `.ai/knowledge/wiki/`

`.ai/knowledge/wiki/` — долгоживущая база знаний проекта.

Сюда попадает не каждая задача, а только стабильные знания:

- доменная модель;
- правила работы устройств;
- сценарии звонков;
- статусы;
- IPC / Electron / preload;
- SIP / WebRTC / controller integration;
- архитектурные решения;
- ограничения продукта;
- повторяемые workflow;
- ответы на вопросы, которые пригодятся в следующих задачах.

## 2.5. `.ai/knowledge/raw/`

`.ai/knowledge/raw/` — исходные материалы.

Примеры:

- описание текущей реализации;
- выгрузка из Jira;
- заметки по референсному ПО;
- скриншоты;
- фрагменты требований;
- технические исследования;
- материалы встреч.

Файлы в `raw/` считаются источниками. Не изменяй их без явной просьбы пользователя.

# 3. Когда нужен план

План нужен, если пользователь явно просит план или задача большая/рисковая.

План обязателен, если задача:

- затрагивает несколько файлов или модулей;
- меняет бизнес-логику;
- меняет архитектуру;
- меняет работу устройств, звонков, статусов, IPC или интеграций;
- требует миграции данных или изменения контрактов;
- может повлиять на существующие сценарии пользователя;
- должна выполняться в несколько коммитов.

План не обязателен, если задача маленькая и точечная:

- исправить опечатку;
- поправить один стиль;
- добавить простой guard;
- исправить очевидный локальный баг;
- выполнить небольшую правку без изменения архитектуры и доменной логики.

Даже без плана изменения должны быть минимальными и проверяемыми.

# 4. Правила планирования

Если пользователь попросил план или задача требует плана:

1. Не вноси кодовые правки до одобрения плана.
2. Сначала изучи входные данные, `.cursor`, релевантные файлы, существующие планы и wiki-страницы.
3. Найди номер задачи.
4. Если номер задачи отсутствует, спроси пользователя номер задачи и не создавай план до уточнения.
5. Создай или обнови `.ai/tasks/WUI-XXXX/case.md`.
6. Создай новый `implementation_plan_N.md`.
7. После создания плана остановись и жди команды пользователя:
   - `одобряю`;
   - `начинай`;
   - `можно делать`;
   - другая явная команда на старт.
8. Не начинай реализацию сразу после создания плана.

# 6. Реализация по шагам

После одобрения плана:

1. Выполняй только текущий шаг.
2. Не делай изменения из будущих шагов.
3. Не меняй план молча.
4. Если план оказался неверным, остановись и предложи корректировку.
5. Используй точечные патчи.
6. После шага выполни доступную проверку.
7. Если проверка невозможна, честно укажи почему.
8. Сообщи пользователю:
   - что сделано;
   - какие файлы изменены;
   - как проверить;
   - что нужно закоммитить;
   - какой следующий шаг после коммита.
9. Жди, пока пользователь подтвердит, что сделал коммит.
10. Только после подтверждения коммита переходи к следующему шагу.

Если контракт, модель или визуальное поведение активно уточняются между шагами, не закрепляй промежуточные решения большим набором новых тестов на каждом шаге. Сначала стабилизируй контракт минимальными проверками, затем добавь или обнови основные тесты отдельным финальным тестовым шагом. Исключение — рискованная бизнес-логика, багфикс или регрессия, где тест нужен сразу для безопасного изменения.

Если пользователь сказал, что сделал `stash`, прими это как сигнал исправить текущий шаг, а не переходить дальше.

Если пользователь после коммита дал новое уточнение, зафиксируй его:

- в `case.md`, если это уточнение по текущей задаче;
- в `.ai/knowledge/wiki/`, если это долгоживущее знание проекта;
- в новом плане, если это меняет будущую реализацию.

# 7. Работа с project wiki

## 7.1. Когда читать wiki

Перед анализом большой задачи или задачей, которая затрагивает доменную логику:

1. Прочитай `.ai/knowledge/wiki/index.md`, если он существует.
2. Найди релевантные страницы.
3. Читай только релевантные страницы, а не всю wiki подряд.
4. Проверь `.ai/knowledge/wiki/product/open-questions.md`, если задача касается спорной или неясной логики.
5. Если нужной страницы нет, не создавай её автоматически без необходимости. Добавь создание страницы в план или спроси пользователя, если это отдельная работа.

## 7.2. Когда обновлять wiki

Обновляй wiki, если в задаче появилось или изменилось долгоживущее знание:

- правило доменной модели;
- поведение устройств;
- поведение звонков;
- логика Speakers/PTT;
- логика конференций;
- правила Directory;
- статусы абонентов;
- IPC-контракт;
- архитектурное решение;
- интеграционный контракт;
- ограничение продукта;
- повторяемый технический workflow.

Не обновляй wiki ради:

- временного debug;
- одноразовой ошибки окружения;
- мелкой CSS-правки;
- промежуточного эксперимента;
- изменений, которые не дают нового знания о проекте.

## 7.3. Как обновлять wiki

1. Не выдумывай факты.
2. Если факт взят из кода, укажи источник: `Источник: path/to/file.ts`.
3. Если факт взят из слов пользователя, укажи: `Источник: уточнение пользователя от YYYY-MM-DD`.
4. Если это предположение, явно пометь: `Предположение`.
5. Если есть противоречие со старой страницей, добавь блок `Противоречия / уточнения`.
6. Нерешённые вопросы добавляй в `.ai/knowledge/wiki/product/open-questions.md`.
7. При создании или существенном изменении страницы обнови `.ai/knowledge/wiki/index.md`.
8. Добавь запись в `.ai/knowledge/wiki/log.md`.
9. Не смешивай wiki-правки с кодовыми правками другой темы.

## 9.3. `.ai/knowledge/wiki/index.md`

`index.md` — каталог wiki.

Обновляй его при создании или существенном изменении страниц.

Пример:

```markdown
# Project Wiki Index

## Product

- `product/overview.md` — общее описание продукта.
- `product/glossary.md` — словарь терминов.
- `product/open-questions.md` — открытые вопросы.

## Domain

- `domain/calls.md` — модель звонков.
- `domain/devices.md` — модель устройств.

## Decisions

- `decisions/adr-001-...md` — краткое описание решения.
```

## 9.4. `.ai/knowledge/wiki/log.md`

Не переписывай старые записи без явной просьбы пользователя.

# 10. Работа без плана

Если пользователь не просил план и задача маленькая:

1. Прочитай релевантные файлы.
2. Сделай минимальное изменение.
3. Не затрагивай несвязанные участки.
4. Выполни доступную проверку.
5. Кратко сообщи результат.

Если в процессе стало понятно, что задача больше, чем казалась:

1. Остановись.
2. Объясни, почему нужен план.
3. Предложи создать `case.md` и `implementation_plan_N.md`.
4. Не продолжай реализацию без согласования.

# 11. Проверки

Перед завершением шага выполни проверки, подходящие задаче:

- `npm run lint`
- `npm run test`
- `npm run ts:check`
- `npm run build`
- точечный unit test
- ручная проверка сценария

Не запускай тяжёлые команды без необходимости, если задача локальная.

Если проверка не запускалась, укажи причину.

Если проверка упала, не скрывай ошибку. Укажи:

- какая команда упала;
- в чём ошибка;
- связана ли ошибка с текущей правкой;
- что предлагается делать дальше.

---

# 12. Ответ пользователю после действия

Отвечай кратко и по делу.

После создания плана:

- где создан `case.md`;
- где создан `implementation_plan_N.md`;
- сколько шагов в плане;
- что нужно сделать пользователю дальше: просмотреть и написать `одобряю` / `начинай`.

После реализации шага:

- что сделано;
- какие файлы изменены;
- какая проверка выполнена;
- что нужно закоммитить;
- какой следующий шаг после коммита.

После обновления wiki:

- какие страницы обновлены;
- какие источники использованы;
- какие открытые вопросы добавлены.

Не пиши длинные отчёты, если пользователь просит кратко.
Не скрывай проблемы, ошибки проверки или сомнения.

# 13. Короткое правило для выбора места хранения

Используй это правило всегда:

```text
AGENTS.md
  постоянные правила работы агента

.ai/tasks/WUI-XXXX/case.md
  описание конкретной задачи

.ai/tasks/WUI-XXXX/implementation_plan_N.md
  план конкретной части задачи

.ai/knowledge/raw/
  исходные материалы

.ai/knowledge/wiki/
  долгоживущие знания проекта
```

Если сомневаешься, куда положить информацию:

- временная информация по текущему багу → `.ai/tasks/WUI-XXXX/case.md`;
- шаги реализации → `.ai/tasks/WUI-XXXX/implementation_plan_N.md`;
- стабильное правило продукта или архитектуры → `.ai/knowledge/wiki/`;
- исходный документ или скриншот → `.ai/knowledge/raw/`;
- постоянное правило поведения Codex → `AGENTS.md`.

# 14. Интеграция с Cursor AI skills

В проекте могут использоваться глобально установленные Cursor skills из `cursor-ai`.

Они разрешены для:
- загрузки Jira-задач;
- анализа связанных задач;
- получения TestRail-контекста;
- получения GitLab-активности;
- ревью кода;
- упрощения кода;
- Figma-анализа;
- подготовки Jira-комментариев;
- публикации в Confluence.

Но они не заменяют локальный workflow проекта.

При любом конфликте между Cursor skill и этим `AGENTS.md` приоритет имеет `AGENTS.md`.

Обязательные правила:
1. После `начинаем` Jira-задача должна быть зафиксирована в `.ai/tasks/WUI-XXXX/case.md`.
2. Для большой задачи должен быть создан `.ai/tasks/WUI-XXXX/implementation_plan_N.md`.
3. Реализация начинается только после явного одобрения плана.
4. После каждого шага пользователь сам коммитит изменения, если явно не попросил агента сделать коммит.
5. Долгоживущие знания фиксируются в `.ai/knowledge/wiki/`.
6. Исходные материалы фиксируются в `.ai/knowledge/raw/`.
7. Confluence не заменяет `.ai/knowledge/wiki/`; он используется только для публикации готовых материалов наружу.
