# WUI-5084 — New Media Devices Stores

## Исходная задача

Постепенно заменить раздутые старые сторы устройств:

- `src/shared/composables/state/devices-store/use-devices-store.ts`
- `src/shared/composables/state/devices-sessions-store/use-devices-sessions-store.ts`

Нужно создать новые сторы параллельно со старыми:

- `src/shared/composables/state/devices-store-new`
- `src/shared/composables/state/devices-sessions-store-new`

После стабилизации новой модели приложение будет переключено на новые сторы, а старые будут удалены.

Первая часть кейса — сделать базовый стор устройств для дальнейшего расширения: собрать доступные браузерные аудио входы и выходы, определить минимальные типы и публичный API.

## Уточнения пользователя

- Номер задачи: `WUI-5084`.
- На первом этапе делаем только базовый `devices-store-new`; `devices-sessions-store-new` создаем как заготовку для будущих шагов.
- Совместимость со старой логикой не нужна.
- IndexedDB больше не будет: хранение будет на backend.
- Сейчас не нужно делать максимально похоже на старые сторы; нужно сделать правильно и лаконично.
- Пользователь должен видеть доступные аудио устройства, которыми можно пользоваться в приложении: привязывать к сессии, выбирать вход/выход и т.д.
- Реальные моковые данные лежат в `src/__mocks_/mock-media-devices.ts`.
- На первом этапе работаем на моках, но production-store не должен импортировать моковые данные напрямую.
- Контроллерные модули не входят в базовый media devices store.
- Подсветка кнопок, снятие трубки, нажатия Goose/PTT и другие аппаратные события относятся к controller layer, а не к базовому стору browser media devices.
- Для будущей маршрутизации звука можно использовать точечное сопоставление по контракту имен, например `goose_L1` / `handset_L1` -> `Module_L1`, но не хранить постоянную синхронизацию controller modules и `enumerateDevices()`.
- USB-гарнитура не требует controller module: она появляется в `enumerateDevices()` и может использоваться через `getUserMedia`, `setSinkId` или Web Audio.
- Пользовательские настройки вроде иконки, номера на кнопке, режима, echo cancellation, noise suppression, auto gain control пока не входят в базовую модель endpoint store. Их нужно закладывать позже в логическую модель профиля/маршрута, если она понадобится.
- В базовом списке устройств нужны только audio input/output.
- Из списка нужно исключать `deviceId === 'default'`.
- Из списка нужно исключать echo-cancelled варианты, например label с `echo cancelled`.
- `groupId` сохраняем как поле браузерного устройства, но не группируем по нему на первом этапе.
- Тесты на первом этапе не пишем.

## Ограничения

- Не переключать текущих потребителей приложения на новые сторы в первой части.
- Не менять старые сторы в рамках этой части.
- Не добавлять новые зависимости.
- Не добавлять IndexedDB, backend API или controller-state в базовый `devices-store-new`.
- Не создавать legacy-compatible API ради старых вызовов.
- Соблюдать FSD и public API через `index.ts`.
- Не делать автоинициализацию при создании стора; инициализация должна быть явной.
- Обработка `devicechange` должна быть идемпотентной и иметь cleanup.
- В рабочем дереве уже может существовать незакоммиченная папка `src/shared/composables/state/devices-store-new`; перед реализацией нужно читать ее содержимое и работать с ним, не перетирая пользовательские изменения.

## Дополнительные уточнения пользователя от 2026-06-23

- В `WUI-5084` входит финализация новых `devices-store-new` и `devices-sessions-store-new`, переключение старых мест приложения на новые сторы и удаление старых стор.
- Backend в рамках этой части не трогаем.
- Приложение должно само определять доступные устройства. Пользователь не должен собирать трубку из отдельных входа и выхода.
- Пользователю нужно показывать готовые logical devices: Goose, Handset и пользовательские/внешние аудио устройства.
- Трубки работают как связанная пара input/output; внешние USB/headset устройства могут отображаться как отдельные input/output endpoints.
- Controller modules по возможности не хранить в `devices-store-new`; старые сценарии подсветки, поднятия трубок, Goose/PTT должны сохраниться через controller/session слой.
- Нужно автоматически получить список доступных устройств для пользователя, включая Goose и Handset по браузерным labels `Module_*`.
- В модель logical device нужно заложить настройки `echoCancellation`, `noiseSuppression`, `autoGainControl`, `icon`, `iconNumber`, `order`, `mode`, `pttScope`.
- Старую логику pinned device пока не переносить полностью: временно использовать первый доступный Goose. Дальше пользователь сможет выбирать конкретный Goose для конкретной группы завершенных вызовов.
- Новый `devices-sessions-store-new` должен сохранить функциональность, необходимую для текущих вызовов: binding сессий, переключение аудио устройства, Handset/Goose runtime state, PTT, hold и cleanup stream.
- В задачу входит переключение controller handlers (`gooseEventHandler.ts`, `handsetEventHandler.ts`) на новые сторы.
- В задачу входит переключение call flows на новые сторы.
- На время миграции новые сторы импортировать под старыми именами `useDevicesStore` и `useDevicesSessionsStore`; после удаления старых стор новые папки/файлы можно переименовать в старые имена.
- Settings UI пока адаптировать минимально, чтобы не ломался. Полноценная настройка устройств может уйти или измениться.
- Если кейс удастся закрыть функционально, в финальной части нужно добавить необходимые тесты.
- Целевое продуктовое направление: пользователь в основном выбирает устройства для групп завершенных вызовов, например один из доступных Goose. Логика трубок зашита в коде и привязана к окну вызовов.

## Уточнение пользователя от 2026-06-24

- Для построения logical devices можно использовать реальные controller modules из `command_exec.modules`, если controller подключен.
- `enumerateDevices()` остается источником реальных browser `deviceId` для аудио входов/выходов.
- Controller modules должны использоваться как источник типа, доступности и hardware identity устройства (`goose_L1`, `handset_L2`, `audiolabel`, `features`, `sources`, `sinks`), но без возврата старой тяжелой синхронизации, IndexedDB и controller-managed profile логики.
- Целевой flow для построения устройства: `command_exec.modules` определяет logical device, `audiolabel`/`sources`/`sinks` связывают его с endpoint из `enumerateDevices()`.
- Controller events позже должны искать logical device по hardware id/module, например `goose_L1` или `handset_L2`.
- Новые сторы не должны проектироваться как совместимость со старыми внутренними типами. Старые места приложения будут переписаны на новые модели, а старые сторы удалены.
- Суть старых функций нужно сохранить на уровне пользовательских сценариев: выбор устройства, привязка сессии, переключение аудио, Goose/PTT, Handset pickup/hangup и подсветка. Внутреннюю реализацию можно и нужно упрощать под новую модель.
