# WUI-4864 — статусы карточек панели быстрого вызова

## Исходная задача

Кейс связан с панелью быстрого вызова и продолжает работу после WUI-4733.

Нужно добавить расширенные статусы карточек контактов панели быстрого вызова. В первой части кейса реализуются только статусы карточек, без действий при клике.

Текущая карточка панели быстрого вызова уже показывает базовые состояния `online` и `offline` на основе SIP/BLF presence. Для WUI-4864 нужно добавить отдельный слой звонковых статусов поверх текущего presence, чтобы карточка могла визуально показывать состояние абонента и звонка.

## Первая часть кейса

Первая часть WUI-4864: добавить отображение расширенных статусов карточек панели быстрого вызова без действий по клику.

Предварительный набор статусов для обсуждения:

- `offline` — контакт не зарегистрирован или статус отсутствует.
- `online` — контакт зарегистрирован, активного звонкового состояния нет.
- `incoming-self` — этот абонент звонит текущему пользователю; цвет зависит от priority группы: high priority — красный, обычная priority — оранжевый.
- `outgoing-self` — текущий пользователь звонит этому абоненту.
- `connected-self` — текущий пользователь находится в разговоре с этим абонентом.
- `conference-self` — текущий пользователь находится в конференции с этим абонентом.
- `incoming-hold-self` — входящий вызов с этим абонентом на удержании.
- `outgoing-hold-self` — исходящий вызов с этим абонентом на удержании.
- `conference-hold-self` — конференция с этим абонентом на удержании.
- `incoming-subscriber` — у абонента есть входящий вызов не с текущим пользователем.
- `connected-subscriber` — абонент находится в разговоре не с текущим пользователем.
- `hold-subscriber` — вызов абонента не с текущим пользователем находится на удержании.

Источники для определения статусов:

- `useContactStatusState().contactStatuses` — базовый SIP/BLF presence.
- `useContactStatusState().lines` или `findLinesByInternalNumber()` — BLF-линии абонента.
- `useSessionStore()` — локальные SIP-сессии текущего пользователя.
- `STATE` из `call-session` и `CallStatusState` из `contact` — состояния локальной сессии и BLF-линии.

Ожидаемый результат первой части:

- Карточка панели быстрого вызова визуально различает базовые статусы, наши directional-статусы и статусы абонента.
- Существующие `online/offline` продолжают работать.
- Действия при клике отсутствуют или остаются без новой бизнес-логики.
- Архитектура WUI-4733 сохраняется: табы, загрузка контактов и SIP/BLF-подписка остаются на своих текущих уровнях.

## Вторая часть кейса

Вторая часть WUI-4864: добавить сетку карточек панели быстрого вызова и базовые операции управления принадлежностью контактов к активной группе через backend API.

Перед основной реализацией нужен подготовительный шаг: создать локальный MCP-сервер для Swagger/OpenAPI организации, чтобы Codex мог находить endpoint'ы, DTO и security requirements без ручного копирования Swagger. MCP-сервер должен запускаться локально через STDIO, жить в `.ai/mcp/swagger/`, читать `SWAGGER_BASE_URL`, `SWAGGER_SPEC_URL` и `SWAGGER_TOKEN` из env, а токен должен храниться только в Windows User env `SWAGGER_TOKEN`. Реальная настройка Codex MCP хранится в пользовательском `%USERPROFILE%\.codex\config.toml`, не в репозитории.

Функциональность сетки:

- Карточки контактов активной группы отображаются в grid-сетке с ячейками.
- Пользователь должен иметь возможность располагать контакты в нужном порядке.
- Если backend предоставляет поле или endpoint для порядка/позиции контактов в группе, нужно использовать backend-контракт.
- Если backend не предоставляет подходящего поля порядка/позиции, на текущем этапе порядок хранится локально во frontend-модели.
- Целевой будущий backend позиций должен возвращать раскладку вида `{ groupGuid, items: [{ contactGuid, cellIndex }] }`.
- В обычном режиме пустая ячейка отображается как пустое место сетки.
- В режиме редактирования пустая ячейка отображает кнопку/иконку добавления контакта.
- В режиме редактирования карточка показывает кнопку с тремя точками. Полноценное контекстное меню можно не реализовывать; для текущей части допустима простая кнопка удаления.

Функциональность добавления контакта:

- Добавление выполняется только в активную группу ПБВ.
- Для выбора контакта можно использовать существующее модальное окно.
- Предпочтительная существующая модалка: `BindingContactModal`.
- `BindingContactModal` уже использует `useContactFiltering`, который вызывает `useContactApi().fetchContacts` и endpoint `GET /api/user/contacts`.
- После выбора контакта нужно отправить запрос на backend для добавления принадлежности контакта к активной группе.
- После успешного ответа backend нужно обновить список контактов активной группы.
- Если выбранный контакт уже есть в активной группе, повторное добавление ничего не делает.

Функциональность удаления контакта:

- Удаление выполняется только из активной группы ПБВ.
- Удаляется только принадлежность контакта к группе, сам контакт из справочника не удаляется.
- На текущем этапе удаление можно реализовать тестово через кнопку удаления в режиме редактирования.
- После успешного ответа backend нужно обновить список контактов активной группы.

Обработка ошибок:

- На текущем этапе достаточно логировать ошибки backend в консоль.
- Отдельный error state, notification/toast или rollback UI во второй части не обязательны.

Ожидаемый результат второй части:

- В ПБВ есть сетка карточек активной группы с поддержкой пустых ячеек.
- В режиме редактирования пустые ячейки позволяют начать добавление контакта.
- Базовое добавление контакта в активную группу работает через backend API.
- Тестовое удаление принадлежности контакта к активной группе работает через backend API.

### Новый backend-контракт fast-dial

### Правила интеграции fast-dial

- В текущей части важнее всего распределение карточек по сетке.
- Количество ячеек сетки ограничено: 36.
- `contacts[].order` в fast-dial трактуется как индекс ячейки сетки (`cellIndex`), а не как плотный порядковый номер.
- Пустые ячейки между карточками допустимы и должны сохраняться.
- Frontend должен предотвращать создание невалидных `order` за пределами сетки.
- Если backend вернул `order` за пределами лимита, frontend показывает только карточки в пределах лимита.
- Если fast-dial содержит `contactGuid`, которого нет в соответствующей группе старого backend, такую позицию не показываем.
- Если в старой backend-группе есть контакт без позиции в fast-dial, кладем его в первую свободную ячейку.
- Если старая backend-группа существует, но fast-dial group для нее еще нет, показываем дефолтную раскладку по порядку контактов.
- Fast-dial group не создается на загрузке страницы только ради дефолтного отображения. Создаем запись в fast-dial только при первом изменении раскладки пользователем.
- С 2026-06-16 backend готов для целевого сценария: ПБВ должна работать только с группами `type: 'user'`; `predefined`/`predefinedShared` больше не используются для отображения ПБВ.
- Целевое будущее состояние: ПБВ работает только с `user` группами, созданными пользователем для себя.
- Пагинации в сетке ПБВ не будет.

### Пользовательские сценарии третьей части

- Если у пользователя еще нет `user` групп — создание через `+` у табов (см. план 8).
- Если `user` группы уже есть, ПБВ отображает их и применяет fast-dial раскладку к карточкам.
- Справа от табов — `+` как в браузере для создания новой пустой группы.
- Добавление контакта в сетку: старый backend добавляет контакт в группу, новый fast-dial backend сохраняет позицию карточки.
- Если сохранение позиции после добавления не прошло, контакт остается в группе старого backend; при следующей загрузке он попадет в первую свободную ячейку.
- Перемещение внутри группы: меняется только fast-dial порядок/позиции, старый backend состава группы не трогаем.
- Перемещение в другую группу: старый backend меняет принадлежность контакта к группам, fast-dial обновляет раскладку исходной и целевой групп.

- Удаление из группы: старый backend удаляет принадлежность контакта к группе, fast-dial удаляет позицию карточки из раскладки группы.
- Пользователь может иметь один контакт в разных группах, но не должен дублировать один контакт внутри одной группы.

## Уточнения от 2026-07-14: device affinity на incoming (бизнес-модель)

Цель: при поступлении звонка сразу понимать «куда пришёл» (goose/pin или left/right handset) для иконок ПБВ/футера, без hold и без media до answer.

### Разделение понятий

- **Affinity** — привязка сессии к устройству без hold и без media (`currentDevice` / mapping для UI и маршрутизации).
- **Activation** — ответ: media (`getUserMedia` / tracks) + hold соседних сессий на трубке при необходимости.

### Правила incoming

1. Если у `pServed` в `usePinnedCallsPanelStore` есть **свободный** слот → affinity на goose (`readyGooseDevices[0]` пока), assign session в свободный слот panel store, **не** показывать в call-card / очереди трубки (ещё до runtime при необходимости — критерий «уходит в pin»).
2. Если слоты по `pServed` есть, но **свободных нет** → как обычный incoming на **выбранную трубку** (affinity handset), **показывать** в call-card.
3. Если слотов по `pServed` нет → affinity на выбранную трубку, в call-card как обычный incoming.
4. Смена selected handset сама по себе affinity **не** меняет; звонок остаётся на текущем affinity, пока нет явного переноса на другую трубку.
5. Явный перенос на другую трубку (ещё RINGING) → rebind affinity на target, без hold и без media.
6. Answer → media + hold других на целевой трубке (и rebind, если ответ с другой трубки, чем affinity).

### ПБВ / исходящие с pin-контакта

- Контакт с ПБВ/панели завешенных: звонок **всегда через goose** (исключения «позвонить с трубки» нет; отдельный сценарий позже).
- Если goose не ready — **не** звонить с трубки; показать ошибку конфигурации устройств (как ContactViewCard / goose handler).
- Сравнение «контакт в panel» — по ключу SIP user (`sip:NUMBER@…`), не только exact `pServed` (домен/`imLogin` у карточки ПБВ может отличаться от слота).
- `usePinnedCallsPanelStore` должен быть загружен **до** клика по ПБВ и до incoming (не только на странице завешенных): bootstrap в `LayoutApplication` + refetch при открытии ПБВ. Иначе `getSlotsByPServed` пустой → ложный handset-path.
- Завешенные не должны отображаться в карточке вызова, когда звонок ушёл в pin/goose.

### Фильтр call-card (согласовано как 3')

Не в call-card / очереди трубки, если звонок **уходит или уже в pin** (есть свободный слот → goose path, или session уже в `slotSessionIds`).  
Если свободных слотов нет и path = handset — **в** call-card.

### Инфра

- Incoming-assign перевести со старого `usePinnedCallsStore` на `usePinnedCallsPanelStore`.
- `bindSessionToDevice` (или новый affinity API) должен уметь режим **без hold** и **без media** на RINGING.
- Делается отдельным планом внутри WUI-4864 (`implementation_plan_7`), домен call-session / devices / call-card + panel store; UI ПБВ потребляет результат.

- Кнопки: «Создать» / «Отмена» (+ close в header).
- После успеха: `refreshTabs()` и переключение на новую группу.
- **Backend issue (2026-07-15):** `POST /api/user/groups` и `GET /api/user/groups/{guid}` видят новую группу, но `GET /api/user/groups` (и `/api/Group/list`) её не возвращают. Это баг бэкенда; frontend-workaround не делаем — чиним на стороне API.
- Ошибки: **нотификация** (как в текущем group store).

### Удаление

- Крестик на табе только в **edit mode** и только на **активном** табе.
- Без confirm-диалога / без success-нотификации удаления (ошибки — с нотификацией).
- Два запроса при удалении:
  1. `DELETE /api/v1/me/fast-dial/groups/{id}` — если для группы есть fast-dial layout (lookup по `groupGuid`, путь использует fast-dial `id` существующего API);
  2. `DELETE /api/user/groups/{guid}` — удаление backend-группы.
- Можно удалить **последнюю** группу: остаётся надпись «список групп пуст» и только кнопка `+`.
- UI Kit: `@wui/common-library` + проектные `MyBtn` / `MyInput` / токены темы.
