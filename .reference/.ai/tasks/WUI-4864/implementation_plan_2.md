# Кейс: WUI-4864 — сетка карточек ПБВ и управление контактами группы

## Описание текущей части кейса

Вторая часть WUI-4864: добавить сетку карточек панели быстрого вызова и базовые операции управления принадлежностью контактов к активной группе через backend API.

Полный план второй части пока не фиксируется. После настройки Swagger MCP и проверки OpenAPI план будет уточняться по ходу реализации.

# План реализации: вторая часть WUI-4864 — начальные шаги

## Шаг 1: Локальный MCP-сервер для Swagger/OpenAPI

- **Описание:** Создать локальный MCP-сервер в `.ai/mcp/swagger/` на TypeScript/Node.js с официальным SDK `@modelcontextprotocol/sdk`. Сервер должен запускаться через STDIO, читать `SWAGGER_BASE_URL`, `SWAGGER_SPEC_URL`, `SWAGGER_TOKEN` из env, не хранить и не логировать токен. Реализовать tools `get_openapi_spec`, `search_api`, `describe_endpoint`, `call_api_get`. Добавить README с инструкцией для пользовательского `%USERPROFILE%\.codex\config.toml`, без создания `.codex/` в репозитории.
- **Файлы для изменений:** `.ai/mcp/swagger/package.json`, `.ai/mcp/swagger/tsconfig.json`, `.ai/mcp/swagger/src/index.ts`, `.ai/mcp/swagger/README.md`.
- **Ожидаемый результат:** Codex сможет подключать локальный MCP-сервер и использовать Swagger/OpenAPI организации для поиска endpoint'ов и описания DTO. Токен передается только через Windows User env `SWAGGER_TOKEN`.
- **Проверка:** `npm install`, `npm run typecheck`, `npm run build`, ручной запуск `npm run start`. Если из текущей среды нет доступа к `192.168.232.234`, зафиксировать это и оставить инструкцию проверки на машине пользователя.
- **Коммит после шага:** Да.
- **Нужно ли обновить project wiki:** Нет.

## Шаг 2: Уточнить backend-контракт групп контактов через MCP Swagger

- **Описание:** Через созданный MCP Swagger найти endpoint'ы для получения контактов активной группы, добавления контакта в группу, удаления контакта из группы и возможного хранения порядка/позиции карточек. Дополнительно сверить существующие frontend API-паттерны проекта и модалку выбора контакта. Зафиксировать методы, paths, DTO, параметры, security requirements, существующий API-слой и используемый модалкой endpoint в `case.md`, не выдумывая контракт.
- **Файлы для изменений:** `.ai/tasks/WUI-4864/case.md`; при необходимости следующий `implementation_plan_2.md` будет дополнен или создан отдельный план следующей части по договоренности.
- **Ожидаемый результат:** Понятно, есть ли на backend поле/endpoint для порядка карточек. Понятно, какие запросы использовать для добавления и удаления принадлежности контакта к активной группе. Зафиксировано, что frontend-запросы нужно делать через существующий axios + `getAppURL` API-слой, а для выбора контакта можно переиспользовать `BindingContactModal`, которая использует `GET /api/user/contacts`.
- **Проверка:** Ответы tools `search_api` / `describe_endpoint` по relevant endpoint'ам; при необходимости безопасные GET-проверки через `call_api_get`.
- **Коммит после шага:** Да.
- **Нужно ли обновить project wiki:** Нет, если это только task-specific контракт. Да, если будет выявлено долгоживущее правило backend-интеграции ПБВ.

## Шаг 3: Базовая модель сетки активной группы ПБВ

- **Описание:** Добавить widget-level модель сетки карточек активной группы: ячейки, занятые контакты, пустые места, порядок карточек. Текущие backend endpoint'ы контактов не поддерживают порядок, поэтому на этом этапе layout хранится локально во frontend-модели. Модель должна быть совместима с будущим backend позиций формата `{ groupGuid, items: [{ contactGuid, cellIndex }] }`: сохранять пустые ячейки, игнорировать stale `contactGuid`, класть новые контакты без позиции в первую свободную ячейку и уметь быть адаптированной к преобразованию `positions -> layout -> positions`. Не добавлять backend-запросы изменения состава группы в этом шаге, кроме уже существующей загрузки активной группы.
- **Файлы для изменений:** `src/widgets/quick-call-panel/model/**`, при необходимости `src/widgets/quick-call-panel/ui/QuickCallPanel.vue`, тесты модели.
- **Ожидаемый результат:** Контакты активной группы могут быть представлены как grid-модель с пустыми ячейками и стабильной раскладкой на уровне frontend-state. Модель остается widget-level composable, а не Pinia store; решение о store откладывается до появления контракта второго backend и требований к синхронизации positions.
- **Проверка:** Точечные unit-тесты модели сетки: заполненные ячейки, пустые ячейки, сохранение порядка, отсутствие дублей.
- **Коммит после шага:** Да.
- **Нужно ли обновить project wiki:** Нет.

## Шаг 4: Визуальная сетка и режим редактирования

- **Описание:** Подключить grid-модель к UI панели быстрого вызова. В обычном режиме пустая ячейка остается пустой. В режиме редактирования пустая ячейка показывает кнопку/иконку добавления, а карточки показывают кнопку с тремя точками. Полноценное контекстное меню пока не реализовывать.
- **Файлы для изменений:** `src/widgets/quick-call-panel/ui/QuickCallPanel.vue`, `src/widgets/quick-call-panel/ui/QuickCallContactCard.vue`, `src/widgets/quick-call-panel/test/**`, при необходимости model-файлы edit mode.
- **Ожидаемый результат:** ПБВ визуально соответствует целевой сетке из скриншотов: карточки занимают ячейки, пустые места видны в edit mode через кнопку добавления, карточки в edit mode имеют affordance для будущих действий.
- **Проверка:** Точечные component tests по ПБВ/карточке; ручная проверка UI в обычном режиме и edit mode.
- **Коммит после шага:** Да.
- **Нужно ли обновить project wiki:** Нет.

## Дальше план уточняется

Следующие шаги не фиксируются до проверки Swagger/OpenAPI и первых изменений сетки. Предварительно ожидаются:

- базовое добавление контакта в активную группу через backend API и существующее модальное окно;
- тестовое удаление принадлежности контакта к активной группе;
- обновление списка активной группы после успешного ответа backend;
- минимальная обработка ошибок через console log;
- подключение отдельного backend хранения позиций карточек, когда будет готов контракт `{ groupGuid, items: [{ contactGuid, cellIndex }] }`;
- уточнение, нужен ли Pinia store для positions, если появятся shared cache, loading/error/save state, debounce сохранения, retry или переиспользование вне ПБВ.
