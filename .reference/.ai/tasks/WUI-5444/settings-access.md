# Settings access: user vs admin (WUI-5444)

Статус: **согласовано 2026-08-26**.  
Паттерн как в диспетчерском пульте: после PIN Settings **расширяется**, а не уходит в отдельный админ-продукт.

---

## Правило

1. **Один ресурс / один DTO на раздел** (`main`, `media`, forwarding, …). Не плодим отдельные `/admin/settings/...` ради UI.
2. У поля или секции есть метаданные доступа: `access: 'user' | 'admin'`.
3. **UI:** без PIN видны только `user`; после PIN появляются:
   - доп. **поля/блоки** внутри уже открытых разделов;
   - целые **вкладки** с `access: admin` (Forwarding, Prioritization, Logs, …).
4. Сейчас в Main и Media admin-полей **нет**, но они **могут появиться** позже — модель должна это допускать (добавляем поля с `access: admin`, ресурс тот же).
5. **Backend (желательно):** GET раздела может отдавать полный DTO; запись `admin`-полей/разделов — только при активной admin-сессии (после проверки PIN/пароля). Детали unlock — отдельный контракт (рядом с WUI-4281). Пока PIN может жить на клиенте, но целевое состояние — проверка на write.

## Как писать в моделях разделов

В каждом `backend-*-settings-model.md`:

- кратко сослаться на этот файл;
- в таблице/DTO пометить `access` у полей (сейчас везде `user`, если не сказано иное);
- при появлении admin-поля — не менять path ресурса, только добавить поле + `access: admin`.
